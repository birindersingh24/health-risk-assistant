# CLAUDE.md

A learning repo (`finops-poc`, NestJS 12 + TypeScript, ESM). It has two separate tracks. Keep them apart: they solve different kinds of problems.

| Track | Problem shape | Technique |
|---|---|---|
| A · FinOps agent | Answers are **computed** from many billing rows (sums, medians, joins) | Agentic loop + SQL tools. **Not RAG.** |
| B · GraphRAG knowledge base | Answers are **written down** in a few passages of text | Chunk + embed, vector store, knowledge graph, RAG |

Rule of thumb: if a human would answer with Ctrl+F and reading, it's RAG. If they'd use a pivot table, it's tools + SQL.

See also `AGENTS.md` (production telemetry via NestJS Observe).

npm run start:dev     # Nest in watch mode

## Track A · FinOps agent

Data: `mocks/focus_mock_costandusage.csv`, a FOCUS 1.2 billing export generated by `mocks/generate_focus_mock.py`. The anomalies planted in it are listed in `mocks/anomalies.json`. Use them as the answer key for tests and evals.

`mocks/checks.sql` holds seven DuckDB checks: spike, sustained_increase, idle, orphaned, commitment, untagged, new_expensive. Each check is one agent tool. The SQL computes the findings and the LLM only explains them.

Target design:
1. Load the CSV into DuckDB (`@duckdb/node-api`) once at startup.
2. Expose each check as a typed tool (name, description, JSON-schema input such as thresholds, date range, account).
3. Run the agent loop server-side: call the LLM with the tools → run any `tool_use` → send back the `tool_result` → repeat until it answers. Cap iterations.
4. Optionally add a read-only `query_costs` tool with a guarded SQL surface (read-only connection, `SELECT` only, row limit).

Don't embed billing rows. `src/csv-chunks/` embeds each CSV row with all-MiniLM-L6-v2. That was the first experiment, and it doesn't work for this data: numbers don't embed meaningfully, top-k can't aggregate, and every row has near-identical text. Reuse that code for Track B instead.

## Track B · GraphRAG knowledge base

Source: `docs/index.html` (the GraphRAG Field Guide). It's an interactive architecture map. Its content lives in the `DETAILS` and `GLOSSARY` objects in the inline script. The guide's examples are Python/LangChain; port them to TypeScript here (LangGraph.js, `@huggingface/transformers`, `neo4j-driver`).

Goal: a Q&A system over team knowledge (Slack, GitHub, Confluence, or local Markdown to start).

### Phase 1 · Build knowledge (offline, never in the request path)
- **Sources / connectors**: one `Document` shape: `id` (`"confluence:48213"`), `text`, `url`, `author`, `updated_at`, `acl`. Capture ACLs at ingestion; you can't recover them later. Sync incrementally with a per-source `updated_since` cursor, and handle deletes.
- **Chunk + embed**: split along structure (headings, functions, Slack threads), ~300–800 tokens with 10–15% overlap. Use deterministic chunk IDs, `sha1(doc_id + ":" + index)`, so re-runs upsert. Attach metadata (doc_id, source, url, updated_at, acl). Embed in batches. Pin the embedding model and store its name on the collection (all-MiniLM-L6-v2 = 384 dims).
- **Entity extraction** (LLM): define the ontology first, e.g. nodes Person, Team, Repo, Service, PR, Doc; edges OWNS, AUTHORED, MODIFIES, DEPENDS_ON. Use a small model with structured output, and resolve entities ("K8s" = "Kubernetes"). Record the source chunk of each fact. Run extraction on a queue, not inline. Skip the LLM where the data is already structured (GitHub API).

### Knowledge layer
- **Vector store** (Chroma to prototype, or pgvector, Weaviate, Qdrant): cosine distance, HNSW. Name collections with a version (`chunks_v1`), since a new chunker or model means re-indexing into `chunks_v2` and then switching over. Add hybrid search (BM25 + vectors) for exact tokens like `ERR_4012`.
- **Knowledge graph** (Neo4j): uniqueness constraints on entity keys, `MERGE` for writes, `(:Chunk)-[:MENTIONS]->(:Entity)`. Cypher can't parameterize relationship types, so use a generic `REL {type}`. Bound traversals to 1–2 hops with `LIMIT`, and watch for hub nodes.
- Use the **same chunk ID in both stores** and delete from both in the same job. Neo4j's vector index can hold everything in one database.

### Phase 2 · Answer (online, a LangGraph state machine)
`query → top-K → related nodes → assemble → grade → generate`, with a `grade → rewrite → query` loop capped by an `attempts` counter.
- **Query**: embed with the exact ingestion model. Rewrite follow-ups into standalone questions. Optional multi-query or HyDE.
- **Top-K**: over-fetch 20–50, and apply the ACL filter inside the query (not after it).
- **Related nodes**: seed from the entities in the top chunks and traverse 1–2 hops into short fact lines. Use templated Cypher only, with read-only credentials.
- **Assemble**: rerank with a cross-encoder down to the top 5–8, dedupe (MMR), put the strongest chunks first or last, number sources `[n]`, stay under the token budget.
- **Grade**: a rerank-score floor first, then a small-LLM structured verdict. When retries run out, answer "not found".
- **Generate**: answer only from the context, cite `[n]`, allow "I couldn't find this", wrap context in `<context>` and treat it as data (prompt injection). Temperature 0, streamed.

### Run & improve
- **Evals before tuning**: a golden set of 30–200 real questions with expected source + answer. Retrieval metric: recall@k (no LLM needed). Generation metrics: faithfulness and relevance (LLM judge + rubric). Run in CI and fail on regressions.
- **Ops**: tracing per node, TTFT and streaming, a semantic cache **keyed by ACL**, an alert on stale sync, PII redaction.

### Build order (from the guide)
1. One source, plain vector RAG: connector → chunk + embed → vector store → top-K → LLM.
2. Write the golden set and measure recall@k.
3. Add reranking and query rewriting (cheap, biggest wins).
4. Add entity extraction + Neo4j once relationship questions appear ("who owns X", "what depends on Y").
5. Move the query flow into LangGraph once you need grading, retries or routing.

### Pitfalls to avoid
- Building the graph before vector retrieval works and is measured.
- Mixing embedding models, or querying with a different model than you ingested with.
- Random UUID chunk IDs (duplicates), forgotten deletes, dropped ACLs.
- Changing chunk size without re-running evals.
- Unbounded loops or traversals. Letting the LLM write arbitrary Cypher or SQL.
